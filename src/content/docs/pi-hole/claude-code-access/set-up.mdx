## Create the Agent User

<Tabs syncKey="cc-identity">
<TabItem label="Your login user">

Nothing to create. Claude Code runs as your existing account.

Skip to [Install Claude Code](#install-claude-code).

</TabItem>
<TabItem label="Dedicated agent user">

<Verified date="2026-08" method="tested" />

<Steps>

1. Create the user with a home directory and no `sudo` group membership:

   <Tabs syncKey="cc-location">
   <TabItem label="On the Pi">

   ```shell title="From the Pi"
   sudo useradd -m -s /bin/bash claude-agent
   ```

   </TabItem>
   <TabItem label="From a workstation">

   ```shell title="From your workstation"
   ssh -t pi-hole-admin 'sudo useradd -m -s /bin/bash claude-agent'
   ```

   </TabItem>
   </Tabs>

1. Tighten its home directory so other accounts can't read its session data:

   <Tabs syncKey="cc-location">
   <TabItem label="On the Pi">

   ```shell title="From the Pi"
   sudo chmod 750 /home/claude-agent
   ```

   </TabItem>
   <TabItem label="From a workstation">

   ```shell title="From your workstation"
   ssh -t pi-hole-admin 'sudo chmod 750 /home/claude-agent'
   ```

   </TabItem>
   </Tabs>

1. Give it a working directory, since Claude Code needs somewhere it can write:

   <Tabs syncKey="cc-location">
   <TabItem label="On the Pi">

   ```shell title="From the Pi"
   sudo -u claude-agent mkdir -p /home/claude-agent/pihole
   ```

   </TabItem>
   <TabItem label="From a workstation">

   ```shell title="From your workstation"
   ssh -t pi-hole-admin 'sudo -u claude-agent mkdir -p /home/claude-agent/pihole'
   ```

   </TabItem>
   </Tabs>

1. Set up access to the account:

   <Tabs syncKey="cc-location">
   <TabItem label="On the Pi">

   Allow your own account to become it. This rule lets you *become* `claude-agent`. It grants `claude-agent` nothing:

   ```shell title="From the Pi"
   echo "$USER ALL=(claude-agent) ALL" | sudo tee /etc/sudoers.d/claude-agent-switch && \
     sudo chmod 440 /etc/sudoers.d/claude-agent-switch && \
     sudo visudo -c -f /etc/sudoers.d/claude-agent-switch
   ```

   The last command should report `parsed OK`.

   </TabItem>
   <TabItem label="From a workstation">

   :::note[Two different SSH problems can look identical]
   If you haven't set up your own `pi-hole-admin` SSH access yet and hit `Permission denied (publickey,password)`, that's an ordinary "this key was never added to that account" problem, fixed with a plain `ssh-copy-id` against your own login. It has nothing to do with the `claude-agent` account below, even though the error text is the same.
   :::

   Give the account its own SSH key so your workstation can reach it directly:

   ```shell title="From your workstation"
   ssh-keygen -t ed25519 -f ~/.ssh/claude-agent -C "claude-agent@pi-hole"
   ```

   Add a second host alias for it, alongside the `pi-hole-admin` one you defined earlier:

   ```text title="~/.ssh/config"
   Host pi-hole-agent
       HostName 192.168.0.153
       User claude-agent
       IdentityFile ~/.ssh/claude-agent
       IdentitiesOnly yes
   ```

   :::caution[Don't reach for `ssh-copy-id`]
   It has nothing to authenticate against: `useradd` leaves this account password-locked by design, so there's no password login for `ssh-copy-id` to use.
   This is the thing most people try first here, and it can't work.
   :::

   Install the key through your administrative session instead:

   ```shell title="From your workstation"
   PUBKEY="$(cat ~/.ssh/claude-agent.pub)" && \
     ssh -t pi-hole-admin "
     sudo -u claude-agent mkdir -p -m 700 /home/claude-agent/.ssh
     echo '$PUBKEY' | sudo -u claude-agent tee -a /home/claude-agent/.ssh/authorized_keys >/dev/null
     sudo -u claude-agent chmod 600 /home/claude-agent/.ssh/authorized_keys"
   ```

   The key goes into a shell variable rather than through a pipe on purpose.
   Piping into `ssh -t` suppresses the terminal it just asked for, and `sudo` on the far end fails with the same password prompt error this page opened with.

   Safe to re-run: doing this twice appends a duplicate identical line to `authorized_keys` rather than breaking anything.
   If you're not sure whether the key's already there, dedupe it:

   ```shell title="From your workstation"
   ssh -t pi-hole-admin "sudo -u claude-agent bash -c 'sort -u -o /home/claude-agent/.ssh/authorized_keys /home/claude-agent/.ssh/authorized_keys'"
   ```

   Leaving the account password-locked is the point.
   The key is the only way in, and it opens a shell with no `sudo` behind it.

   Confirm the alias lands in the right account, and do this before touching any Pi-hole data:

   ```shell title="From your workstation"
   ssh -o ConnectTimeout=8 -o BatchMode=yes pi-hole-agent 'id'
   ```

   That should report `uid=... (claude-agent)`, which is sshd enforcing the identity rather than Claude Code choosing it.
   `BatchMode=yes` makes this fail fast and non-interactively instead of hanging on a password prompt, and running it now isolates "is the SSH layer working" from "does this account have the Pi-hole permissions it needs," two separate failures that are easy to conflate if the first query you try is a real one.

   Setup commands on the rest of this page use `pi-hole-admin`, because they need `sudo`.
   Claude Code only ever uses `pi-hole-agent`.

   </TabItem>
   </Tabs>

</Steps>

## Grant Read Access

<Verified date="2026-08" method="tested" />

POSIX ACLs grant one account read access to one file.
Unlike group membership, an ACL can be scoped per file, is revocable without touching the account, and grants no write access anywhere.

Every command in this section runs with `sudo` on the Pi.

<Steps>

1. Install the ACL tools. They aren't present by default:

   <Tabs syncKey="cc-location">
   <TabItem label="On the Pi">

   ```shell title="From the Pi"
   sudo apt install acl
   ```

   </TabItem>
   <TabItem label="From a workstation">

   ```shell title="From your workstation"
   ssh -t pi-hole-admin 'sudo apt install acl'
   ```

   </TabItem>
   </Tabs>

1. Apply the grant. Three `setfacl` calls, chained so the run stops if any one fails:

   <Tabs syncKey="cc-location">
   <TabItem label="On the Pi">

   <Tabs syncKey="cc-identity">
   <TabItem label="Your login user">

   ```shell title="From the Pi"
   sudo setfacl -R -m "u:${USER}:rX" /var/log/pihole && \
     sudo setfacl -m "d:u:${USER}:r" /var/log/pihole && \
     sudo setfacl -m "u:${USER}:r" /etc/pihole/pihole-FTL.db && \
     sudo setfacl -m "u:${USER}:r" /etc/pihole/pihole-FTL.db-wal /etc/pihole/pihole-FTL.db-shm
   ```

   </TabItem>
   <TabItem label="Dedicated agent user">

   ```shell title="From the Pi"
   sudo setfacl -R -m u:claude-agent:rX /var/log/pihole && \
     sudo setfacl -m d:u:claude-agent:r /var/log/pihole && \
     sudo setfacl -m u:claude-agent:r /etc/pihole/pihole-FTL.db && \
     sudo setfacl -m u:claude-agent:r /etc/pihole/pihole-FTL.db-wal /etc/pihole/pihole-FTL.db-shm
   ```

   </TabItem>
   </Tabs>

   </TabItem>
   <TabItem label="From a workstation">

   <Tabs syncKey="cc-identity">
   <TabItem label="Your login user">

   Replace `pi-admin` with your own account name on the Pi:

   ```shell title="From your workstation"
   ssh -t pi-hole-admin 'sudo setfacl -R -m u:pi-admin:rX /var/log/pihole && \
     sudo setfacl -m d:u:pi-admin:r /var/log/pihole && \
     sudo setfacl -m u:pi-admin:r /etc/pihole/pihole-FTL.db && \
     sudo setfacl -m u:pi-admin:r /etc/pihole/pihole-FTL.db-wal /etc/pihole/pihole-FTL.db-shm'
   ```

   </TabItem>
   <TabItem label="Dedicated agent user">

   ```shell title="From your workstation"
   ssh -t pi-hole-admin 'sudo setfacl -R -m u:claude-agent:rX /var/log/pihole && \
     sudo setfacl -m d:u:claude-agent:r /var/log/pihole && \
     sudo setfacl -m u:claude-agent:r /etc/pihole/pihole-FTL.db && \
     sudo setfacl -m u:claude-agent:r /etc/pihole/pihole-FTL.db-wal /etc/pihole/pihole-FTL.db-shm'
   ```

   </TabItem>
   </Tabs>

   </TabItem>
   </Tabs>

</Steps>

Explanations:

- `-R -m u:...:rX` on the log directory
  - `X` means "execute only on directories," so the directory gets `r-x` and every log file gets `r--`.
  - A lowercase `r` here instead breaks the whole grant, and fails in a way that looks like the ACL never applied: a named-user entry replaces whatever the account was getting from the directory's "other" class, so `u:agent:r--` on the directory strips the execute bit it needs to enter the directory at all, and every read below it is denied.
- `d:u:...:r` on the log directory
  - Sets a default ACL, which is what survives log rotation.
  - Pi-hole rotates `pihole.log` daily and `FTL.log` weekly with `create 640 pihole pihole`, building a brand new file each time. An ACL set only on today's file is gone tomorrow. A default ACL is inherited by every file created in the directory afterward, including the compressed `.1` and `.2` archives.
- `u:...:r` on the query database
  - Needs no directory ACL: `/etc/pihole` is already world-traversable.
  - This grant also survives Pi-hole restarts. FTL resets the database to mode `0640` every time it starts, and `chmod` rewrites an ACL's mask rather than removing named-user entries, so the read stays effective.
- `u:...:r` on `pihole-FTL.db-wal` and `pihole-FTL.db-shm`
  - `pihole-FTL.db` runs in SQLite's WAL journal mode, so a reader also needs to open these two sidecar files. Granting the `.db` file alone fails with `Parse error in 3rd command line argument: unable to open database file (14)`, an error that reads like a syntax problem and isn't.
  - This has to be a per-file grant, not a default ACL on `/etc/pihole` itself. That directory also holds `pihole.toml`, which this guide separately and correctly keeps off limits (it stores API password hashes in plaintext); a directory-wide default ACL would silently expose it to any account with the default grant.
  - Not yet confirmed whether this grant survives an FTL restart the way the `.db` grant does. FTL may recreate `-shm` on restart the same way it resets the database's mode, which would drop the ACL along with it. If queries that worked start failing with the same error after restarting FTL, re-run this command.

:::note[If you ever delete the FTL database]
FTL creates a fresh `pihole-FTL.db` when the file is missing, and the new file has no ACL.
Re-run the third and fourth commands if you delete or restore that database.
:::

## Read Query History

<Verified date="2026-08" method="vendor-docs" />

`pihole-FTL` ships an embedded SQLite shell, so no separate `sqlite3` package is needed.
Always pass `--readonly`, which makes writes impossible at the connection level.

Run this as the account you just granted access to. It doubles as proof the grant works.
Replace `YOUR-DEVICE-IP` with the IP of a device on your network you want to check:

<Tabs syncKey="cc-location">
<TabItem label="On the Pi">

```shell "YOUR-DEVICE-IP" title="From the Pi"
pihole-FTL sqlite3 --readonly /etc/pihole/pihole-FTL.db \
  "SELECT datetime(timestamp,'unixepoch','localtime'), client, domain, status
   FROM queries
   WHERE client = 'YOUR-DEVICE-IP'
   ORDER BY timestamp DESC LIMIT 20;"
```

</TabItem>
<TabItem label="From a workstation">

<Tabs syncKey="cc-identity">
<TabItem label="Your login user">

```shell "YOUR-DEVICE-IP" title="From your workstation"
ssh pi-hole-admin "pihole-FTL sqlite3 --readonly /etc/pihole/pihole-FTL.db \
  \"SELECT datetime(timestamp,'unixepoch','localtime'), client, domain, status
    FROM queries
    WHERE client = 'YOUR-DEVICE-IP'
    ORDER BY timestamp DESC LIMIT 20;\""
```

Nested double quotes around the SQL string get easy to get subtly wrong once you're wrapping an already-quoted command in `ssh host "..."`.
A heredoc avoids the extra escaping layer entirely and matches the multi-line SQL formatting above verbatim:

```shell "YOUR-DEVICE-IP" title="From your workstation"
ssh pi-hole-admin bash -s <<'EOF'
pihole-FTL sqlite3 --readonly /etc/pihole/pihole-FTL.db \
  "SELECT datetime(timestamp,'unixepoch','localtime'), client, domain, status
   FROM queries
   WHERE client = 'YOUR-DEVICE-IP'
   ORDER BY timestamp DESC LIMIT 20;"
EOF
```

</TabItem>
<TabItem label="Dedicated agent user">

```shell "YOUR-DEVICE-IP" title="From your workstation"
ssh pi-hole-agent "pihole-FTL sqlite3 --readonly /etc/pihole/pihole-FTL.db \

```

```shell "YOUR-DEVICE-IP" title="From your workstation"

```

</TabItem>
</Tabs>

</TabItem>
</Tabs>

The `queries` view resolves the internal integer IDs back to real domain and client strings, so you don't need to join anything.
`status` stays numeric.

The values are:

| Status | Meaning |
|--------|---------|
| `1`    | Blocked by a blocklist (gravity) |
| `2`    | Forwarded upstream |
| `3`    | Answered from cache |
| `4`    | Blocked by a regex filter |
| `5`    | Blocked by the denylist |

The database lags live traffic by up to 60 seconds because FTL flushes its in-memory buffer on `database.DBinterval`, which defaults to `60`.

## Configure Claude Code

<Verified date="2026-08" method="vendor-docs" />

Permission rules are enforced by Claude Code, not the kernel.

Claude's own documentation notes that Bash patterns constraining arguments are fragile, so these rules are defense in depth: they stop an honest mistake, and the ACL is what holds when a rule is bypassed.

That ordering matters most for `pihole.toml`, since on a `0644` host the deny rule is the only thing standing between an agent and your password hashes.

<Tabs syncKey="cc-location">
<TabItem label="On the Pi">

Add to `~/.claude/settings.json` in the home directory of the account Claude Code runs as:

```json title="~/.claude/settings.json"
{
  "permissions": {
    "deny": [
      "Read(/etc/pihole/pihole.toml)",
      "Bash(sudo:*)"
    ],
    "allow": [
      "Bash(pihole-FTL sqlite3 --readonly:*)",
      "Bash(pihole status)",
      "Bash(dig:*)",
      "Bash(tailscale status)"
    ]
  }
}
```

</TabItem>
<TabItem label="From a workstation">

Add to `.claude/settings.json` in the project directory you run Claude Code from:

<Tabs syncKey="cc-identity">
<TabItem label="Your login user">

```json title=".claude/settings.json"
{
  "permissions": {
    "allow": [
      "Bash(ssh pi-hole-admin:*)"
    ]
  }
}
```

### What ACL for Claude Code Can and Can't Do

`pi-hole-admin` is your own account, so the `allow` rule lets Claude Code run anything on the Pi as you, `sudo` included if your account has passwordless `sudo` (even if temporarily because you entered the password recently).

The ACL and the file modes are the only real limits, which is the tradeoff you accepted by running as your login user.

</TabItem>
<TabItem label="Dedicated agent user">

```json title=".claude/settings.json"
{
  "permissions": {
    "deny": [
      "Bash(ssh pi-hole-admin:*)",
      "Bash(ssh -t pi-hole-admin:*)"
    ],
    "allow": [
      "Bash(ssh pi-hole-agent:*)"
    ]
  }
}
```

The deny rules keep Claude Code off the administrative alias, so it can't reach the account that has `sudo`.
`claude-agent` account's own permissions on the Pi restrict the agent alias itself, not the contents of this file.
