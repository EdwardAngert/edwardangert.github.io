Give Claude Code limited access to Pi-hole logs and the query database so that it can help you diagnose issues with your Pi-hole setup.

Use the steps on this page to decide how you access your Pi-hole and how you'll interact with Claude Code in order to diagnose and resolve the Pi-hole issues.

The access you give Claude Code with these steps is read-only, and limited in scope to Pi-hole-specific files.

## Why sudo Isn't the Answer

<Verified date="2026-08" method="tested" />

Claude Code runs as whatever user starts it.
No separate service account exists to add to a group, and no setting changes which Unix user its commands run as.

So if that account already has `sudo`, why not let it use it?
The answer depends on something you should check first:

```shell title="From the Pi"
sudo -n true && echo "passwordless sudo: ENABLED" || echo "sudo asks for a password"
```

Both results lead to the same conclusion, by opposite routes.

### If sudo Asks for a Password

Claude Code runs shell commands with no terminal attached, and `sudo` needs one to prompt:

```shell title="How Claude Code's shell sees it"
sudo cat /var/log/pihole/pihole.log
```

```text
sudo: a terminal is required to read the password; either use the -S option to read from standard input or configure an askpass helper
sudo: a password is required
```

The problem isn't that you lack privilege. It's that an agent can't answer a password prompt.

### If sudo Is Passwordless

This is the more common case on a Pi-hole box.
Raspberry Pi OS enabled passwordless `sudo` by default until the 6.2 release in April 2026, and **that release only changed the default for new installations**.
An older Pi, or one that has been upgraded rather than reimaged, still has it unless someone turned it off.

Here the command works. That is the problem.

Passwordless `sudo` doesn't give Claude Code access to your Pi-hole logs.
It gives it unrestricted root on the Pi, non-interactively, for every command it decides to run.
Reading the query log, yes, and equally `pihole -g`, restarting DNS, rewriting `pihole.toml`, or deleting something you needed.
Nothing sits between a misread instruction and the machine.

Setting up SSH keys doesn't change this either way.
Key-based login authenticates you to the *host* and hands you a shell as your own account. It grants no root at all.
Passwordless `sudo` is a separate setting, and it is the one that removes the gate.

You can turn it off in `raspi-config` under **System Options**, or in the Control Centre **System** tab on Raspberry Pi OS Desktop.

### Either Way, the Fix Is the Same

If `sudo` prompts, the agent can't do the reads you want.
If `sudo` doesn't prompt, it can do everything you don't.

That leaves two honest fixes: make the specific data readable without escalation, or allow specific commands without a password.
This page does the first, because it grants less, and because it works the same whichever answer you got above.

## What This Lets Claude Code Do

<Verified date="2026-08" method="vendor-docs" />

The grant on this page is read-only, so Claude Code can **investigate on its own but cannot change anything**.

It can read the query database and the logs, work out which client asked for what and when, find which list blocked a domain, and tell you what to change.
It cannot allow or deny a domain, update gravity, restart DNS, or edit any configuration.

That boundary is firmer than it might look.
`pihole allow` and `pihole deny` don't need root, but they authenticate to Pi-hole's API by reading `/etc/pihole/cli_pw`, which is mode `0640` and owned by `pihole`.
Without that file, the command falls back to an interactive password prompt, which an agent can no more answer than a `sudo` prompt.

:::caution[The boundary only holds if sudo asks for a password]
Everything above describes what the ACL grant allows.
It says nothing about what `sudo` allows.

If the account Claude Code runs as still has passwordless `sudo`, it can bypass all of this by prefixing any command with `sudo`, and the grant on this page becomes decoration.
Turn passwordless `sudo` off for that account, or run Claude Code as a [dedicated agent user](/docs/pi-hole/claude-code-access/#choose-your-setup) that never had it.
:::

### How You Apply the Fixes

Claude Code tells you the command, and you run it yourself using **shell mode**.

Typing `!` at the start of the Claude Code prompt runs the rest of the line as a shell command in your own terminal:

```shell title="At the Claude Code prompt"
! sudo pihole allow ads.example.com
```

Shell mode runs the command directly, without Claude interpreting or approving it, and adds both the command and its output to the conversation.
Claude then reads the result and carries on.

This works precisely because **you have a terminal and the agent does not**, which is the same asymmetry the previous section describes.
A `sudo` prompt can ask you for a password. It cannot ask Claude Code.

The loop is: Claude diagnoses, gives you a command, you run it with `!`, and Claude picks up from the output.

If you would rather Claude Code apply list changes itself, see [Optional: Give Claude Code Write Access](/docs/pi-hole/claude-code-access/extend/#optional-give-claude-code-write-access).

## Which Pi-hole Files Need Access

<Verified date="2026-08" method="vendor-docs" />

Two things need a grant: the query database, and the log files.

| File                        | Mode             | Holds                                      | Needs access? |
|-----------------------------|------------------|--------------------------------------------|---------------|
| `/etc/pihole/gravity.db`    | `0664`           | Blocklists, groups, clients                | No, already world-readable |
| `/etc/pihole/pihole-FTL.db` | `0640`           | Query history                              | **Yes**       |
| `/var/log/pihole/*.log`     | `0640`           | Raw dnsmasq and FTL logs                   | **Yes**       |
| `/etc/pihole/pihole.toml`   | `0640` or `0644` | Full config, **including password hashes** | No, deliberately excluded |

Leave `pihole.toml` alone.
It stores `webserver.api.pwhash` and `webserver.api.app_pwhash` as plain strings, so an agent that reads the file pulls your password hashes into its transcript.
When you need one value from it, read that value on its own:

```shell title="From the Pi"
pihole-FTL --config webserver.api.app_sudo
```

## Choose Your Setup

Two decisions. Pick each once, and the rest of this page follows your choice.

**Where Claude Code runs:**

<Tabs syncKey="cc-location">
<TabItem label="On the Pi">

Claude Code runs on the Pi itself and reads the files directly.
Simplest option, with one hard requirement: Claude Code needs a 64-bit OS and 4 GB of RAM.
That means a Pi 4 with 4 GB or more, or a Pi 5, running the 64-bit Raspberry Pi OS.

Check before you commit to this:

```shell title="From the Pi"
uname -m && free -h | awk '/Mem:/ {print $2}'
```

`aarch64` and 4 GB or more means you're fine.
`armv7l`, or less memory, means use the workstation option instead.

</TabItem>
<TabItem label="From a workstation">

Claude Code runs on your laptop and reaches the Pi over SSH.
Works with any Pi, including a Pi 3, a Zero 2 W, or a 2 GB Pi 4, because the Pi only runs the commands.

This assumes you can already reach the Pi without typing a password.
If a connection prompts for one, set up key-based authentication before going further.
An agent can't answer that prompt any better than it can answer `sudo`.

Define an administrative alias now, because the rest of this page uses it by name:

```text title="~/.ssh/config"
Host pi-hole-admin
    HostName 192.168.0.153
    User pi-admin
```

Replace the address and account with your own, then confirm it works:

```shell title="From your workstation"
ssh pi-hole-admin 'echo connected'
```

:::note[Reading the commands on this page]
Every command still executes on the Pi.
Where the target account matters, this page gives you an explicit workstation version.
Anywhere you see a bare `From the Pi` block, wrap it yourself:

- Without `sudo`: `ssh pi-hole-admin '<command>'`
- With `sudo`: `ssh -t pi-hole-admin '<command>'`

The `-t` is not optional. Without it there's no terminal on the far end, and `sudo` fails with the same error above.

:::

</TabItem>
</Tabs>

**Which account Claude Code runs as:**

<Tabs syncKey="cc-identity">
<TabItem label="Your login user">

Claude Code runs as you.
Nothing to create, and the ACL grants go to your own account.

The tradeoff is blast radius.
Running as your login user, Claude Code can read everything you can: your SSH keys, your dotfiles, your shell history.
That may be entirely fine on a Pi you use for one thing.

</TabItem>
<TabItem label="Dedicated agent user">

Claude Code's commands run as a separate unprivileged user that owns nothing but its own home directory.

This is the tightest option.
A dedicated user with no `sudo` and read-only ACLs can read the Pi-hole data and nothing else: not your SSH keys, not `pihole.toml`, not `/etc/shadow`. It cannot write to the logs it reads or escalate back to your account.

:::note[This has to be enforced, not requested]
No Claude Code setting runs commands as a different user, and instructing it to use one in `CLAUDE.md` is not a boundary.
Permission rules and context files shape what Claude *tries*, not what the kernel *allows*.

The account has to be real at the process level, which works differently in each location:

- **On the Pi**, you start Claude Code from inside that account, once.
- **From a workstation**, you point the SSH alias at that account, and sshd enforces it for every command.

:::

</TabItem>
</Tabs>
