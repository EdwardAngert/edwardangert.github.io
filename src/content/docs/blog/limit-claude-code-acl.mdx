I asked Claude Code to help me diagnose issues with my Pi-hole configuration, and in the process, I learned a few things about how to give Claude Code access to the files it needs without giving it too much access to my files.

This was something I was working on for the [Pi-hole documentation I host on edwardangert.com](../pi-hole/index.mdx) so that I can offer readers a way to troubleshoot safely, but while I was working on it, a friend told me about how he had Claude Code diagnose a compromise he had found on a device on his network.
I told him that I might have something for him.

If you're asking Claude Code, "I think my system's been compromised, help me check it out and harden my settings," this post will get you set up quickly, on a Mac or on Ubuntu, which is the running example for everything below.

The same pattern works for a lot more than system hardening:

- Edit your `.zshrc` for shell settings.
- Manage your dotfiles.
- Poke at your `/etc/hosts` file.
- Maintain your Jellyfin server/library.

Diagnosing these requires read access to logs and configs, and fixing what you find requires write access to specific files, so this post covers both along with some conceptual guidance so you can run through the steps and apply them to your specific needs.

Through these steps, you scope what Claude Code can touch on your machine so that you "don't give the agent more than it needs."

This helps constrain overeager agents and mitigate prompt injection.
Prompt injection and agents ignoring instructions has gotten a lot of attention in the first half of 2026.
If a prompt-injected session can only reach the files you explicitly granted, that's the entire blast radius, whatever the injected instructions say.

## Who Should Use ACL to Limit Claude Code's Access to Files?

Part of what prompted this post is the ample enterprise-grade results for "least privilege for AI agents."
If that's what you need, there are plenty of solutions with teams ready to "hop on a call."

If what you need is Claude Code to help you with your laptop, Raspberry Pi, or that Proxmox Optiplex in your basement, then you've come to the right place.

Here's how to give Claude Code access to what it needs, and nothing more, using access control lists (ACLs) in 2026.

## Ask Claude Code What It Needs First

I wrote about what it's like to [ask Claude what it wants](../what-a-claude-wants-needs.mdx), and in this case, it's a great first step.
Send it in stages rather than one long prompt covering the whole session, so you're in the loop at each decision point instead of reviewing everything at the end.

Bump the reasoning effort up before sending this one (`/effort high` in Claude Code).
This is the stage most likely to pattern-match a plausible-sounding list instead of actually testing each candidate.
A bigger budget buys room to run the check instead of skip it.

This first prompt gives Claude Code (or Cowork) a chance to identify what it needs within a limited scope.
The process of giving it slices of the whole task is called progressive disclosure:

```md
I want you to help me diagnose whether my system's been compromised, and
harden it afterward. I'm doing this over ACLs, not sudo, for the whole
session: you should never run sudo yourself or need a standing credential,
no passwordless entry, no askpass helper, no cached ticket. For a
root-owned file, tell me the exact `chmod +a` or `setfacl` command and
I'll run it myself, that's expected, not a workaround. Don't propose
anything that lets you retrieve or reuse a credential without me typing
it fresh each time. Any time I grant you something, verify it before
treating it as done: re-run the same read or write you needed it for,
don't trust a `chmod` or `setfacl` exit code alone. If an entry shows up
in `getfacl` or `ls -le` but the operation still fails, say so rather than
assuming the grant worked.

First, run only unprivileged, read-only commands (uname, os-release, `ps`,
`ss`/`netstat`, whether a display manager is running, whatever tells you
what you're actually working with) to find out what system this is.
Don't ask me, check.

Then, before you propose anything else, give me two lists, not one:

1. Files and directories you'd need read access to, to diagnose this. Use
   what you know about this kind of system to generate candidates, the
   way any audit would, but before listing one, test it: `cat`, `head
   -c1`, or `ls` against it, and only list what that test actually
   fails on. Say why it failed. On macOS, "permission denied" means an
   ACL will fix it; "operation not permitted" means TCC or SIP is
   refusing above the filesystem, no ACL and no sudo will help, flag it
   and don't propose a grant. On Linux don't assume that same split, a
   MAC system like SELinux or AppArmor can also deny with "permission
   denied," so if a grant doesn't work after it's applied, check
   `dmesg` or `journalctl` before assuming the ACL syntax was wrong. If
   a candidate doesn't exist on this machine, say so instead of listing
   it.
2. Files you'd *guess* you might need write access to, to fix whatever
   you find. Before guessing, search for current hardening guidance for
   the system you identified in step one, don't rely on training data
   alone for anything version- or config-specific. Cite what you found
   next to each guess, and confirm the path still exists on this
   machine before including it, a search result citing an old path
   isn't the same as a path that's actually there. Label the whole list
   speculative. Don't propose it as something to grant yet, we'll
   rebuild it for real after the diagnosis, from what you actually
   found instead of what you're guessing now.

Display both lists here, and also write them to
`./claude-security-audit.md` in the current directory.
```

Instead of translating the read list into commands yourself, ask Claude Code to do it.

Drop effort to medium here, it's turning information it already has into syntax, not open-ended judgment.

```shell title="In Claude Code"
/effort medium
```

```md
Turn the read list into commands I can run, one per line, `setfacl` if
you found Ubuntu, `chmod +a` if you found macOS, quoting `${USER}`
correctly for the shell you identified. Mark which lines need `sudo`
because the file's root-owned, and which don't. Don't run any of them,
just give me the list to review.
```

Review what comes back, and run what you're comfortable with yourself.
Generating the command and running it are two different things, don't hand the second one to Claude Code either.
The worked examples below show what a real list looks like on each platform.
Leave the write list alone. It's speculative, and nothing on it gets granted yet.

Once read access is in place, hand the next stage back.
Keep the effort high for this one too, it's the actual analytical step, correlating what's installed against what's running is exactly the kind of thing a bigger reasoning budget pays for, and it's where a real finding is most likely to get made or missed.

```md
Read access is granted. Run the diagnosis for real.
When you're checking for stale or risky configuration, check what's
installed against what's actually running or loaded, not just one or the
other, they answer different questions.
```

Read what actually comes back before moving on to the last stage.
Effort can drop back to medium here.
The hard part already happened in the diagnosis, this is mapping a confirmed finding to the specific file it needs, one line each, not open-ended judgment.

```md
Based on what you actually found, give me a second, non-speculative write
list, one line per file, scoped to exactly what needs fixing.
```

What comes back is usually a short, specific list, "read the auth log to check for failed login attempts," "write `/etc/hosts` to add the entries we agreed on," and that list is the actual spec for the grants you're about to make.
Each line becomes one ACL command, and nothing gets granted that wasn't on a list you actually reviewed.
Medium effort is also enough for applying the fixes and verifying each grant afterward, mostly mechanical work, but keep it at medium rather than dropping to low: the verification step from the first prompt, checking `getfacl` or `ls -le` instead of trusting an exit code, is exactly the kind of check that gets rubber-stamped under a smaller budget.
Splitting this into three prompts instead of one does for the agent's context what it does for you: each stage only carries what's relevant to it, and you get three points to look at real output and decide something, instead of one long response you either approve wholesale or don't.
It also surfaces the read/write split explained below before you've committed to anything, which is the whole point of asking first instead of granting broadly and narrowing later.

## The Error That Started This

The first thing Claude Code hit wasn't a permissions error.
It was this:

```text
sudo: a terminal is required to read the password; either use the -S option to read from standard input or configure an askpass helper
sudo: a password is required
```

My instinct was to read that as "Claude Code's account needs more privilege."
It didn't.
The account already had `sudo`, the same as mine does when I'm at the keyboard.
The actual problem was narrower: `sudo` wanted to ask a question, and Claude Code runs shell commands with no terminal attached for it to ask into.

That's a small distinction, but it changes what you go looking for.
If you assume the problem is privilege, you'll eventually land on something that removes the password prompt entirely: passwordless `sudo`, an askpass helper, a cached credential.
All three grant *more* than you meant to, because none of them can tell "Claude Code, doing the diagnostic and hardening work I asked for" apart from "anything at all running as this account, forever."
If you instead treat it as an interaction problem, no terminal, you go looking for a way to make specific files readable and writable without asking permission at all, one file at a time, on purpose.
That's a bigger ask than a single read-only grant, but it's still a much smaller ask than root, and it has a mechanism that scales to it.

## Why the Easy Fixes Are the Same Fix Wearing a Costume

Before I settled on the answer, I tried talking myself into each of the easy ones, and they all failed the same test.

- **Passwordless `sudo`.** Removes the prompt for every command, not just the ones I wanted Claude Code to run. Full root, unattended, permanently, which is a much bigger grant than "read my auth log and tighten my SSH config."
- **An askpass helper.** Silences the prompt by handing `sudo` a password from somewhere else, a file, an environment variable, a script. That password now has to live somewhere Claude Code's account can read it. It's not a fix for the problem, it's the problem with an extra step in front of it.
- **A cached `sudo` ticket.** If I type my password once and then start Claude Code in the same terminal, `sudo` caches that authentication for several minutes and Claude Code inherits it silently. No prompt, no visible grant, and no way to tell "this command genuinely needed no privilege" from "this command rode a ticket I authenticated minutes ago."
- **A secrets manager with no fresh human step.** Same shape as the askpass helper, one hop further away. Whatever lets the account decrypt the secret at request time is itself a standing credential.

The test that rules all four out is the same test: does Claude Code's own account end up able to retrieve something that grants more than the specific files it needs?
If yes, it's passwordless `sudo` with extra steps, however it's dressed up.
That test doesn't change when the task grows from "read one log" to "diagnose and fix a system." It just gets applied to more files.

## What an ACL Grant Actually Is

An access control list attaches a permission, read, write, or both, to one specific account on one specific file, outside the normal owner, group, and everyone-else model.
Ubuntu and macOS both have this, but they don't share a command, so this post shows both side by side, and it's worth knowing that up front rather than discovering it mid-command.

**Ubuntu** (and Linux generally) uses `setfacl`, from the POSIX.1e draft ACL implementation.
A read grant looks like this:

```shell
sudo setfacl -m "u:${USER}:r" /var/log/auth.log
```

A write grant is the same command with `w` (or `rw`, if Claude Code needs to read the current value before changing it, which it usually does):

```shell
sudo setfacl -m "u:${USER}:rw" /etc/hosts
```

**macOS** has no `setfacl` at all.
Its ACLs are NFSv4-style, and they're folded into `chmod`, using `+a` to add an entry:

```shell
sudo chmod +a "${USER} allow read" /private/var/log/system.log
```

And a write grant spells the permission out instead of abbreviating it, but it's otherwise the same shape:

```shell
sudo chmod +a "${USER} allow read,write" /etc/hosts
```

Either way, on either platform, that's the whole grant.
Not a Teleporter password, not `NOPASSWD` on a wildcard, not a shell.
Read or write, on the one file Claude Code actually needs for the task in front of it.

No `sudo` is required to use the grant once it's in place, because the operation now succeeds as an ordinary, unprivileged file access.
No credential exists for the agent's account to leak, cache, or hand off to something else, because there was never a password in the picture to begin with.

## The Diagnose-Then-Fix Pattern

"Help me check whether my system's been compromised and harden it," "help me clean up my dotfiles," "help me figure out why my Pi-hole logs look wrong," these all share the same shape.
Each one is really two different access problems wearing one sentence.

**Diagnosis is a read problem, and it's fine for it to be broad.**
Auth logs, listening ports, running processes, startup items, firewall rules, all as they currently stand.
Read access to all of that doesn't let Claude Code change anything, so granting it liberally doesn't cost you the thing this whole approach is protecting: the ability to revoke and walk away clean.

On Ubuntu:

```shell
sudo setfacl -m "u:${USER}:r" /var/log/auth.log
sudo setfacl -m "d:u:${USER}:rX" /etc/ssh
sudo setfacl -m "u:${USER}:r" /etc/crontab
```

On macOS, the equivalent diagnostic targets aren't the same files, and most of them don't need a grant at all.
When I ran the same prompt against my own Mac, the read list Claude Code came back with was headed by `/private/var/log/system.log`, `~/Library/LaunchAgents`, `/Library/LaunchAgents`, `/Library/LaunchDaemons`, and `/etc/pf.conf`, not `/var/log/auth.log`, which doesn't exist there.
I checked all five before granting anything.
Every one of them was already readable by an ordinary admin account, no `chmod +a` needed.
That's not a failure of the diagnosis, it's a real result: macOS ships most of its own logs and startup-item locations world-readable, and a list of files to check is also a list of files to notice are already open.

The one file on this Mac that actually needed a grant wasn't on that list, and it's worth reading anyway, because it answers a question this post already raised: has anything already configured passwordless `sudo`, without me asking for it?

```shell
ls -la /etc/sudoers
```

```text
-r--r-----  1 root  wheel  1709 Aug 12 22:51 /etc/sudoers
```

Root-owned, group `wheel`, mode `0440`.
An ordinary admin account isn't a member of `wheel`:

```shell
id -Gn | tr ' ' '\n' | grep -x wheel
```

Nothing printed, not a member, so:

```shell
head -c 1 /etc/sudoers
```

```text
head: /etc/sudoers: Permission denied
```

"Permission denied," not "Operation not permitted," the filesystem itself is refusing, which is what makes this an ACL problem instead of the TCC kind covered below.
The grant:

```shell
sudo chmod +a "${USER} allow read" /etc/sudoers
```

That `sudo` is mine, typed once, at the keyboard, the same shape as the `/etc/hosts` grant above.
Claude Code never runs `sudo`.
After this one command it reads `/etc/sudoers`, and everything under `/etc/sudoers.d/`, the same way it reads anything else on the granted list.
On a clean install `/etc/sudoers.d/` is empty, which is itself the answer worth having.
If it isn't, that's the finding, since installers for some older Docker- and VirtualBox-era macOS tooling have been known to drop `NOPASSWD` entries in there on install, unprompted.

**Fixing is a write problem, and it has to stay narrow, file by file.**
Once Claude Code tells you what it found, either revoke the read grants and apply the fixes yourself, or grant write access to exactly the files the fix touches, one command per file, not a directory-wide grant and not a second thought.
The value of doing this through Claude Code instead of by hand is that it can read the file, propose the exact diff, and you can review that diff before it's ever written, the same way you'd review a pull request.
The ACL grant is what lets it actually apply the change once you've agreed to it, without you needing to sit at the keyboard typing `sudo` for every line.

## Not Every Write Target Is Equally Safe to Grant

This is the part that matters most if the goal is hardening a system you're worried about, not just editing your own `.zshrc`, so it gets its own section instead of a caveat buried in a list.

A write grant is scoped to a file. It is not automatically scoped to the file's *effect*.
Two files can look equally narrow, one ACL command each, and have wildly different blast radii depending on what reads them and when:

- **Low blast radius:** `/etc/hosts`, on either platform. Something you can write, and the only thing that changes is which IP your machine resolves a hostname to. Nothing re-executes it as a script. Nothing treats it as code.
- **Higher blast radius, still bounded:** on Ubuntu, `/etc/ssh/sshd_config`, `/etc/sysctl.d/*.conf`, a specific `ufw` rules file. Writable, and a privileged process (`sshd`, the kernel at boot, `ufw`) reads the new value and acts on it, but only after a restart or reload you control, and only within that service's own behavior.
- **Effectively root, dressed as a file grant:** on Ubuntu, anything under `/etc/sudoers.d/`, `/etc/cron.d/`, a systemd unit file, `/etc/passwd`'s writable path with shell field access. On macOS, a `/Library/LaunchDaemons/*.plist` with `RunAtLoad` set, which is exactly what a system LaunchDaemon is for, launchd runs its `ProgramArguments` as root the next time it loads, no further gate in between. Write access to any of these is not a scoped grant anymore. It's a way to get root the next time that file is read, and it fails the same test as passwordless `sudo` for the same reason: the account can retrieve something, in this case a write, that lets it become more than the one thing it needed.
- **Not a file, no matter what you grant.** Some macOS posture was never a plist to begin with, or stopped being one. The Application Firewall's state lived at `/Library/Preferences/com.apple.alf.plist` through roughly macOS 12, that path is what a decade of search results and tutorials still point to, and it no longer exists. Current macOS administers the firewall through a helper binary instead:

  ```shell
  /usr/libexec/ApplicationFirewall/socketfilterfw --getglobalstate
  ```

  Reads are unprivileged, writes need root, and there's no file to scope an ACL to either way. If a path a tutorial swears by turns out not to exist on your machine, that's not a broken grant, it's an old tutorial.
- **Not a scoping problem at all, no matter what you grant.** Some files are locked below the point where `setfacl`, or even `sudo`, has any say. On a Mac, `/Library/Application Support/com.apple.TCC/TCC.db`, the database that tracks which apps you've granted camera, microphone, or screen-recording access to, is one of these. macOS protects it with System Integrity Protection (SIP), a kernel-level lock that root itself can't write past without booting into Recovery Mode and turning SIP off first, which is not something you want an agent doing on your behalf. No ACL grant gets you there, and no amount of `sudo` does either. The fix isn't a bigger grant, it's the operating system's own tool: `tccutil reset <service>`, or the System Settings UI, which is how Apple designed the only legitimate path to change it. Linux has its own version of this same wall, an immutable file (`chattr +i`) or a file under mandatory access control (SELinux, AppArmor) will refuse a write from root too, until you go through that system's own tool instead of the filesystem.

This is worth being blunt about, because it's the exact mistake that started the research behind this post in the first place: a setting or a grant that's *named* or *shaped* like something narrow, but isn't narrow in what it actually lets you do.
Before granting write on any file, ask what reads it and whether that reader treats it as data or as instructions, and ask whether the file is even reachable by a write at all.
If the answer is "a root process runs whatever's in this file, no human step in between," that file belongs on your never-grant list regardless of how small the edit looks.
If the answer is "nothing, not even root, can write here without going through the OS's own tool first," stop reaching for `setfacl` and go find that tool instead.

## The Gotchas

This is the part worth writing down, because I only found it by running the commands, not by reading the manual page.

**Directory grants need a capital `X`, not a lowercase `r`, on Ubuntu, and neither one opens the files inside.**
A lowercase `r` on a directory strips the search bit, because a named-user ACL entry *replaces* what the account was getting from "other," it doesn't add to it, so the account can list names but can't `cd` in or reach anything below.
Grant `rX` instead (`X` sets execute only on directories and files that already have it set for someone), and the account can traverse the directory and reach files by name.
It still can't read their contents.
That takes a separate grant on the files themselves: `-R` for what's there now, a default ACL for what shows up later.

**Per-file grants on rotated logs die at the next `logrotate` run, on Ubuntu.**
Rotation creates a new inode for the fresh log file.
The ACL you set on the old file doesn't travel with the name.
The fix is a *default* ACL on the directory, not the file, which new files inherit automatically:

```shell
sudo setfacl -m "d:u:${USER}:r" /var/log
```

**Use `${USER}`, not `$USER`, if a colon-suffix like `:r`, `:w`, or `:rX` follows it, and you're in zsh, on Ubuntu.**
This one cost me an afternoon.
zsh treats an unbraced `$USER` immediately followed by `:r` as a parameter-expansion modifier, borrowed from history substitution, and silently eats the suffix, even inside double quotes.
`u:$USER:r` quietly becomes `u:myuser`, not `u:myuser:r`.
`setfacl` rejects that outright, `Option -m incomplete`, exit code 2, it doesn't grant something broken or grant nothing silently.
The danger isn't a bad grant, it's where the error lands: buried in the middle of a longer block of commands, scrolled past, while the actual symptom shows up later, somewhere else, a file that should be readable isn't, with no obvious link back to a quoting bug two commands earlier.
bash doesn't have this problem.
Braces around the variable are a no-op in bash, so `${USER}` is the safe form in both shells, and it costs nothing to always write it that way.
This is specifically a `setfacl` problem, `$USER` isn't followed by a bare colon anywhere in the macOS `chmod +a` syntax, so it doesn't apply there, but bracing it costs nothing on either platform, so this post does it everywhere.

**A service's own startup `chmod` can silently switch your grant off, on Ubuntu, without deleting it.**
Several services `chmod` their own config on every restart.
That doesn't remove your ACL entry.
`chmod` rewrites the ACL's *mask*, and the mask is a ceiling every named entry sits under.
Grant `u:${USER}:r`, and a later `chmod 600` on the same file drops the mask to `---`.
Your entry is still listed in `getfacl`, right where you left it, and stops working anyway:

```text
user:claude:r--	#effective:---
mask::---
```

`getfacl` still shows the entry, so a check that only greps for the username reports success on a grant that's actually dead.
Check the `#effective:` column instead:

```shell
getfacl -p /etc/some-service.conf | grep 'effective:---'
```

Any output means the grant has been masked off, possibly since the last time that service touched its own permissions.

**On macOS, `-R` only grants what already exists, not what shows up later, and a directory needs a different permission word than a file, in the same command.**
`chmod -R +a` walks a directory once and writes an entry onto every file it finds at that moment.
A file created a second after doesn't get one.
There's a second trap in the same command, easy to miss because it doesn't look broken: `read` isn't a real permission on a directory.
macOS silently rewrites it to `list`, enumerate names only, no traversal.
The files underneath still show a correct `read` entry in `ls -le`, so it looks granted.
Without `search` on the directory itself, nothing inside is reachable by path anyway, no matter what the file's own entry says.
Grant `list,search,read` together instead, `list,search` cover the directory, `read` covers the files, one recursive command gets both right:

```shell
chmod -R +a "${USER} allow list,search,read" ~/Library/LaunchAgents
```

That's a real gap for exactly the check this grant is usually for.
LaunchAgents and LaunchDaemons are macOS's version of cron and systemd units, the standard place something persists itself to run again after a reboot, and the whole point of reading that directory is to notice something new landing in it.
The forward-looking half is a pair of inherit flags on the directory itself:

```shell
chmod +a "${USER} allow list,search,readattr,readextattr,readsecurity,file_inherit,directory_inherit" ~/Library/LaunchAgents
```

New files now arrive already carrying the entry, marked `inherited` in `ls -le`.
Files that existed before the flags were set get nothing, inheritance isn't retroactive either.
A real persistence check on macOS needs both: `-R` for what's already there, the inherit flags for what arrives next.
Same trap as the Ubuntu `logrotate` gotcha above, in different clothes: recursive is a snapshot, inheritance is a rule.

**On macOS, a granted read can still come back denied, and that's not a bug in the grant.**
When I ran the diagnostic prompt above against my own Mac, Claude Code correctly flagged one file ahead of time: `~/Library/Application Support/com.apple.TCC/TCC.db`, the per-app privacy grants database, normally needs Full Disk Access to read at all, regardless of what the file's own permissions or ACL say. Full Disk Access is macOS's own gate, on top of the filesystem, that decides whether a specific *app* (Terminal, iTerm, whatever's actually running your shell) can reach a short list of protected locations. An ACL grant on the file doesn't touch it. If a read you granted still comes back denied, check System Settings → Privacy & Security → Full Disk Access before assuming the `chmod +a` command failed.

## Verify and Revoke

Confirm any grant, read or write, before you trust it.

On Ubuntu, with `getfacl`:

```shell
getfacl /etc/hosts
```

On macOS, `getfacl` doesn't exist either, use `ls -le`, not `ls -l`:

```shell
ls -le /etc/hosts
```

The distinction matters more than it looks.
`ls -l` marks an ACL with a trailing `+` and an extended attribute with `@`, and shows only one of them.
Nearly every file on a modern Mac carries at least one extended attribute (`com.apple.provenance`, on anything written by an app), so the `@` is almost always there and the `+` never surfaces.
A file with an ACL and a file without one can look identical in `ls -l`.

Remove a grant with one command, no password, no config file, no account change.
Ubuntu:

```shell
sudo setfacl -x "u:${USER}" /etc/hosts
```

macOS needs more care than the parallel command suggests.
`chmod -a` subtracts the permissions you name from a matching entry, it doesn't delete the entry, and it exits `0` whether or not anything matched:

```shell
sudo chmod -a "${USER} allow read" /etc/hosts
```

Revoke a `read,write` grant with a string that only says `read`, and you've released read and kept write, silently, with a success exit code.
Revoke by index instead, using the number `ls -le` already printed:

```shell
sudo chmod -a# 0 /etc/hosts
```

Or clear every entry on the file, which is normal when you're the only one who put ACLs on it:

```shell
sudo chmod -N /etc/hosts
```

Either way, confirm with `ls -le` afterward.
The exit code won't tell you if it worked.
The file will.

That asymmetry is most of the actual payoff, and it matters more for write grants than read ones.
Setting one up correctly, on the right file, took me an afternoon of testing gotchas.
Taking it away takes one line and a follow-up check, touches nothing else about the account or the service, and leaves you back exactly where you started before you asked Claude Code to look at anything.
That's the property that makes it reasonable to grant write access for a hardening session at all: you're never more than one command away from having granted nothing, as long as you check that it worked.

## The General Principle

Grant the narrowest capability that actually answers the question you're asking, for as long as you're actually asking it, and prefer "no credential exists" over "credential is well hidden."
Read broadly for diagnosis, because read access can't make anything worse.
Write narrowly for the fix, one file at a time, and check what reads that file before you grant it.
Revoke when the session's done.

Every one of the easy fixes I tried first failed that test at the privilege stage.
The file that fails it at the *file* stage, `/etc/sudoers.d/`, a systemd unit, a root LaunchDaemon, is the one worth remembering, because it's the same mistake wearing a smaller costume.
